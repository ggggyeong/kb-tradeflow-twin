# 서비스 중심 MVP 구현 기준

목표는 수출기업 담당자의 ‘문서 확인 → 일정 비교 → 관련 자료 확인 → 상담 준비’를 연결하는 것이다. 실제 금융 판단이나 상품 가입을 대신하지 않는다.

## 서비스 계약

| 충돌 코드 | 서비스 코드 | 정보 | 추가 확인 |
| --- | --- | --- | --- |
| WORKING_CAPITAL_LOAN_MATURITY | LOAN_REPAYMENT_REVIEW | 상환 방법·연체·연장 상담 조건 | 잔액·다른 입금·현재 은행 상담 |
| FX_FORWARD_MATURITY | FX_SETTLEMENT_REVIEW | 기존 매도 계약의 결제 의무·손실·중도해지 | 통화·금액·외화 확보·은행의 변경/정산 조건 |
| SUPPLIER_PAYMENT | SUPPLIER_FUNDING_REVIEW | 운전자금 용도·조건 / 확인된 수출채권의 매입 요건·환매·비용 | 실제 필요액·지급 목적·증빙 |

서비스·검색 주제·질문은 `app/services/service_policy.py`가 결정한다. LLM은 이를 바꾸지 않는다. 현재 서비스 카드 상태는 INFORMATION / REVIEW_REQUIRED / NO_CONFLICT다. INFORMATION은 안내 자료가 있다는 뜻이며 이용 가능 판정이 아니다.

## 데이터 흐름

1. Supervisor가 수행할 단계와 순서를 계획한다. 별도 Planner는 없다.
2. Document Agent가 PDF/OCR에서 핵심 값을 제출한다. 코드가 원문·페이지와 대조한다.
3. Finance Agent 도구가 엑셀에서 거래를 연결하고 지원 결제조건의 예상 입금일을 계산한다.
4. 날짜 비교는 Python 규칙으로 실행한다. 미확인·같은 날은 판단을 보류한다.
5. 확정된 충돌만 서비스 정책에 연결한다.
6. 카탈로그의 거래 조건으로 자료를 제한하고, Chroma에서 충돌 코드·자료 ID·본문 주제를 함께 필터링한다.
7. 주제별 검색 본문을 LLM에 제공한다. LLM은 각 자료의 핵심 원문과 출처 ID를 제출한다. 관련 문장이 없으면 null과 경고를 제출한다. 자유 요약은 생성하지 않는다.
8. 코드가 ID 조합·해시·페이지·구간·원문 문장 일치를 검증한다.
9. 서비스 카드에 상황·관련 정보·별도 확인 질문·제한을 담아 보고서를 생성한다.

## 중단 규칙

- 충돌 없음: RAG 생략.
- 날짜·거래 연결·통화·매도 방향 미확인: 입력 확인 요청.
- 수출채권 미확인: 채권 관련 PDF 제외.
- 미검토·비활성 자료, 미지정 본문 구간: 검색 제외.
- 파일·카탈로그가 색인과 다름: 재검토·재색인 요청.
- 근거 없음 또는 검증 실패: 설명 보류. 다른 상품으로 자동 대체하지 않음.

## 보완한 점

이전에는 대출 만기와 공급자 지급이 비슷한 질의로 같은 운전자금 본문을 찾았다. 이제 대출 만기는 상환·연체·연장, 공급자 지급은 용도·조건으로 구분한다.

이전 페이지 단위 검색은 한 페이지에 섞인 다른 상품까지 전달할 수 있었다. 이제 카탈로그의 시작·끝 문구로 검토 구간을 추출하고 topic·section_id를 저장한다. 구간 경계가 바뀌거나 중복되면 색인을 생성하지 않는다.

LLM이 임의로 만들던 확인 질문은 코드의 서비스 체크리스트로 분리했다. 실제 nano 실행에서 금융 요약이 다른 자료의 조건을 혼합하는 경우를 확인해 자유 요약을 제거했다. 보고서에서 코드가 정한 검토 목적, LLM이 선택한 핵심 원문, 추가 확인 질문을 나눈다.

원문 발췌 방식도 선택 문장의 관련성·완전성을 보증하지는 않는다. 실제 계약은행이 자료 발행은행과 같아도 개별 계약 적용 여부는 사람이 확인해야 한다. 금융일정 충돌은 실제 부족액 계산이 아니다.
